## 2026-07-25 17:41 MZC2026 warehouse/wlp22 ERR 調査・count_eq O(P^2) メモリバグ修正

**作業ブランチ**: `fix/count-eq-pending-updates-quadratic`

**実施内容**
- results.csv で唯一 ERR だった warehouse/wlp22 の原因を調査
  - ローカル初回再現の ERR は環境残骸が原因: build/・build-prof/ の mznlib に feature/more_constraint 由来の fzn_global_cardinality*.mzn が残存(7/6 コミット 71fe3aa)。main の fzn_sabori は sabori_global_cardinality 未実装のため「Unsupported constraint」で即死。正本 share/ には無い。残骸4ファイルを削除
  - 正しい mznlib では wlp22 は 90秒で最大 14.5GB を消費(構築2.2GB、残り12GBは探索中に増加)。Challenge のメモリ上限超過 → OOM → ERR が本命
  - massif プロファイル(wlp02)で配置元特定: ピークヒープの90.7%が CountEqConstraint::propagate 内の std::vector<PendingUpdate> 成長(単一ベクタ4.8GB)
- 根本原因: count_eq の forward sweep が enqueue 時に is_possible_ を落とさないため、除去適用ごとに on_set_*/on_remove_value が propagate を再帰呼び出しし、未適用の除去要求を可能変数の数だけ再 enqueue。pending_updates_ は読み取りインデックス方式で fixpoint 終了まで縮まないため O(possible^2) に肥大
- 修正: CountEqConstraint / CountEqVarTargetConstraint の両 propagate で、sweep の enqueue と同時に is_possible_ を先取りで落として trail に記録。callback を is_possible_ ガードで no-op 化し再帰と重複 enqueue を断つ。propagate に save_point 引数を追加、呼び出し14箇所を更新

**設計判断・理由**
- 「先取り更新」方式を採用。最終 fixpoint 状態(除去される値の集合)は不変で、conflict 検出点(ドメイン空化・不変条件違反)も同一なので健全。ただし redundant re-propagation を消すため探索の速さは変わる(軌道可変)
- propagate のシグネチャ変更を選択(virtual override ではない private ヘルパーなので安全)。trail 記録に save_point が必須のため
- 軌道可変は [[constraint-entailment-flag]] 方針どおり許容。判断基準は健全性と net 性能で検証

**検証結果**
- メモリ: wlp22 が 14.5GB → 2.0GB(flatten ベースラインで頭打ち、OOM 解消)
- 健全性: global_cardinality 全解列挙が gecode と完全一致(18/5670/6561/4200/213)
- テスト: C++単体 42916 assertions・fzn 7/7・golden 242 pass/0 fail 全て green

## 2026-07-25 23:45 surface-based-tsp 全滅分析・ネイティブ tree 制約実装

**作業ブランチ**: `feature/native-tree`

**実施内容**
- MZC2026 surface-based-tsp（dual surface TSP、三角形の全域木構造）の 3/5 UNK 原因を分析
  - 標準 TSP successor 形式でなく tree グローバル制約による連結性問題。基盤エラーでなく探索/伝播の敗北
  - 小（burma14=14, ulysses16=16）は解ける（burma14 は Obj=3323 最適、chuffed 一致）。大（berlin52=52, st70=70, ch130=130）は最初の実行可能解に0到達で UNK
  - 原因: (1) tree のネイティブ実装なし → std 分解（parent/dist 距離ラベリング + reified、大域連結性 propagator なし）、(2) LCG なし。chuffed は native tree（chuffed/fzn_tree_int.mzn）+ LCG で解ける。gecode は native tree なし＋実行不可
- ネイティブ TreeConstraint を実装（feature/native-tree, a02d809）
  - es[e]=1 のたびに選択辺から fresh に union-find 構築（ステートレス、backtrack 安全）、閉路検出/予防。辺端点強制・根強制・ns=0伝播。全確定時に木性検証
  - registry に sabori_tree/fzn_tree 登録、mznlib に fzn_tree_int.mzn 配線
  - C++ ブルートフォース全解照合40試行（全列挙）+ minizinc vs chuffed 20試行以上、孤立ノード等も一致

**設計判断・理由**
- union-find は永続 trail+rewind でなくステートレス（毎回モデルから再構築）を採用。O(E)/es=1 だが rewind バグの risk を排除
- node_base は辺端点 min でなく 1 固定（ノードID は 1..N。孤立ノードがあると辺 min が誤り、辺を誤ノードにマップする実バグを踏んだ）

**デバッグで判明した2つの落とし穴（重要）**
- 基底 Constraint::on_instantiate の呼び忘れ: has_uninstantiated が 2WL watch(w1_/w2_)に依存するため、基底を呼んで watch を更新しないと未確定変数を見落とし on_final を早期発火 → 木を構築できず sols=0。circuit/subcircuit は基底を呼んでいた。graph系グローバルを新規実装する際の必須事項
- node_base 誤検出: detect_base(from,to)=min が孤立ノードで 1 にならず辺を誤マップ。ノードID空間（1..N）から決めるべき

**検証結果**
- 健全性: C++ 40試行全列挙 + chuffed 照合、iso（孤立ノード N3E1）も 5=5
- 全 C++ 42916 assertions・非python ctest 263・golden 244 全 green
- 効果: berlin52/st70/ch130 が std 分解 0解UNK → native tree で最初の実行可能解を発見（UNK→S）。burma14 fails 41177→13372。subcircuit/int_times と違い大インスタンスを実際に UNK→S へ押し上げた最大の効果
