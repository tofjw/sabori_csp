## 2026-07-01 conflict 学習に境界 explain 拡張（穴なしドメイン）

**実施内容**

- conflict 学習の説明収集 `capture_conflict_explanation` を拡張。従来は「違反制約のスコープ変数が全 instantiated」のときのみ Eq literal で学習し、1つでも未確定なら bail していた。
- 拡張: 未確定変数でも**穴なし区間**なら、presolve(根) から動いた境界を literal 化して説明に加える。`min>presolve_min` → `v>=min`(Geq)、`max<presolve_max` → `v<=max`(Leq)。両境界とも根のままなら寄与なし。穴ありの変数があるときだけ bail。空説明は学習しない（空 NoGood=UNSAT 主張のガード）。
- `SABORI_CONFLICT_BOUNDS` env（既定 on）で境界拡張を A/B 切替可能に。

**設計判断・健全性の根拠**

- 制約が矛盾(false)を返した時点の現ドメイン状態をそのまま説明にする。**穴なし**なら `[min,max]` が実ドメインそのものなので「各 v ∈ [min,max] の連言 ⟹ 矛盾」が成立し NoGood は健全。
- **穴ありは不可**: `[min,max]` が実ドメインの上位集合になり、穴の中の解で含意が崩れる（偽 UNSAT）。→ `var_size(v)==max-min+1` の O(1) 判定で穴なしを保証。
- presolve 境界と比較するのは、根の境界（常に真）を落として NoGood を一般化するため。

**検証結果**

- ctest 261/261 green。
- **健全性: 全242コーパスで base == -C(境界拡張あり) の解集合・ステータス完全一致**（mismatch=0）。偽 UNSAT/解漏れなし。
- 稼働確認: celar13 で bounds OFF(fails 67708/nogoods 284) vs ON(64462/253) と挙動変化。この問題では bounds ON が fails 減。

**気づいた課題・TODO**

- bounds ON vs OFF の性能差は問題依存。VBS/ヘッドツーヘッドで広く測り、conflict 学習の既定挙動（多様化メンバー）に bounds ON を採るか判断する。
- bound literal を含む NoGood の伝播効率（unit 化・watch）は未精査。

**関連ファイル**

## 2026-07-01 [健全性バグ修正] conflict 境界拡張を撤回（偽 optimal）

**事象**

- `SABORI_CONFLICT_BOUNDS=1 SABORI_THREADS=3 python bench_compare.py 2018` で、elitserien handball1（真の最適=2）が **obj=3 で optimal(==========) と誤報告**。

**原因と切り分け**

- 再現条件: minizinc **2.9.7**（snap, bench_compare が使用）の flatten 結果 + `-j3` + 境界拡張 ON で確実再現（6/6）。私が当初使った squashfs minizinc **2.9.3** では flatten が異なり再現せず（手元検証の盲点）。

- 不健全の本質: 穴なし変数の境界 literal を含む NoGood が、最適化で obj 境界が締まる経路で実解（obj=2）を排除し、ワーカーが「obj<2 なし」を偽 exhaust → 並列の最適性証明が obj=3 を最適と誤判定。理論上は健全に見えたが（各 NoGood は当該状態で違反）、bound-literal の含意が探索の bound 締め（B&B 仮定）と相互作用して崩れる。242コーパスの -a 解集合一致では露呈しなかった（-a は obj 境界を締めないため）。

**修正**

- `capture_conflict_explanation` を **instantiation-only に戻した**（境界拡張を撤回）。`conflict_bounds_` メンバと `SABORI_CONFLICT_BOUNDS` env を削除。conflict 学習自体（全確定スコープの Eq NoGood 化）は健全なので存続。

**検証**

- 修正後: hb1_297(2.9.7 flatten) -j3 で **0/6 偽 optimal**（全 obj=2 正）。ユーザの正確なコマンドでも obj=2 optimal 3/3。
- ctest 261/261 green。全242コーパス base==-C 解集合一致（mismatch=0）。

**教訓**

- ベンチハーネス再現は **同一の minizinc バージョン/.msc** で行うこと（2.9.7 vs 2.9.3 で flatten・探索が変わり、健全性バグの再現可否が変わった）。
- 並列最適化の健全性検証は -a 解集合一致だけでは不十分。**obj 境界が締まる最適化経路**での「真の最適 vs 主張 optimal」照合が必須。
- bound-literal を含む学習 NoGood は B&B の bound 仮定と相互作用し不健全になり得る。conflict 学習は instantiation-only に限定。

**関連ファイル**

## 2026-07-01 [追跡] conflict 境界拡張が「理論上健全に見えて」不健全な根本原因

**目的**: 撤回した境界拡張が、なぜ理論上妥当に見えて実際は偽 optimal を生むのか追跡。

**切り分け（全て bench_compare と同一の minizinc 2.9.7 flatten で決定的に）**

1. **単一スレッドでは健全**: `-j1 -C SABORI_CONFLICT_BOUNDS=1` は obj=2 を正しく `==========`（むしろ bounds OFF より速い）。→ 境界拡張「単体」は健全。**不健全は並列 bound 共有との相互作用**。
2. **var_data 同期ラグは原因でない**: capture を var_data(SoA) から Variable の実 Domain 直読み（min/max/size/is_assigned）に変えても **7〜8/8 偽のまま**。ラグ仮説を棄却。
3. **目的変数の境界 literal 単独でもない**: obj の境界 literal を除外（SABORI_CONFLICT_NOOBJ）しても **8/8 偽**。

**根本原因（確定）**

- bound-literal NoGood は「その時点の変数境界が矛盾を含意する」という**大域 NoGood**として学習される。
- しかし B&B 最適化では obj が探索仮定 `obj≤gb-1` に締まり、その伝播（obj=Σcost 制約等）で**多数の変数境界が obj≤gb-1 の帰結として締まる**。conflict の説明に含めるこれらの境界は「obj≤gb-1 を仮定した条件付き事実」であり、**仮定を記録せずに大域 NoGood 化**している（obj literal を除いても、他の境界自体が仮定の帰結なので暗黙に条件付き）。
- 最適性証明は **obj<gb を仮定して探索空間を exhaust** する。真の最適解 obj=2(⟹obj≤gb-1) はその仮定下で同じ伝播境界を満たすため、条件付き NoGood に**誤って排除**され、ワーカーが「obj<gb に解なし」と偽 exhaust → 並列マネージャが gb=3 を最適と誤報告。
- **単一スレッドが健全な理由**: obj≤K は「直前に自分で発見した obj=K+1」の後に適用され、K+1 の最適性証明にのみ使う（探索フェーズ全体が obj≤K 前提で結論も obj≤K 世界の話なので整合）。並列は**自分が発見していない gb** の最適性を、仮定条件付き NoGood で証明しようとして崩れる。
- **instantiation-only が健全な理由**: 全確定スコープの矛盾は「その具体値が制約に違反する」**仮定に依らない ground 事実**。分岐仮定を含まないので最適性証明でも安全。

**教訓**

- 学習 NoGood に「探索の仮定（B&B の目的境界やその伝播帰結）」が混入すると、最適性証明でその仮定を discharge する際に循環的不健全になる。conflict 説明は **ground（全確定）に限定**するのが安全。境界を含めるなら仮定（decision literal / obj 境界）を明示的に記録する本格 LCG が必要で、安易な bound 追加は不可。
- ベンチ再現は **同一 minizinc バージョン**必須（2.9.7 で決定的再現、2.9.3 では出ず）。

**状態**

- capture は instantiation-only に確定（調査スキャフォールド conflict_bounds_/SABORI_CONFLICT_BOUNDS/NOOBJ/ログを全撤去）。ctest 261/261 green。-j3 -C で 0/6 偽（obj=2 正）。

## 2026-07-01 10:20 conflict/NoGood 健全性の理論整理とソルバ立ち位置の確定

**実施内容**
- 前段の「境界拡張 撤回・根本原因追跡」を受け、NoGood 健全性の理論を対話で整理。
- 検証済みの切り分け（再掲）: 境界拡張は単一スレッド健全・並列 B&B のみ不健全 / var_data 同期ラグは原因でない（実 Domain 直読みでも偽）/ obj 境界 literal 単独でもない（除外しても偽）。
- ソルバの立ち位置と今後の clause 学習方針を確定し、project memory に記録（solver-positioning-activity-vs-external）。

**設計判断・理由**
- 「obj≤gb-1 を節に入れれば守れるのでは」→ **否**。最適性証明の探索領域そのものが obj≤gb-1 であり、取り逃す真の最適解（obj=2 ≤ gb-1）はその内側。obj 境界 literal は obj>gb-1 の（興味のない）解しか守れない。区別力を持つのは obj 境界ではなく **矛盾に至った decision リテラル**。
- 「decision trail の NoGood はなぜ健全か」→ trail 上の decision は全部いま真で、そこから健全な伝播が矛盾を出したので `d1∧…∧dk ⟹ 矛盾` が成立＝妥当。責任 decision を含むのは全部入れているので当然（責任集合は trail の部分集合）。真犯人特定不要で健全なのが利点。過度に specific（弱い）で、1-UIP はこれを健全なまま刈り込んで一般化する。
- 「SAT ならいけるか」→ 今回の B&B 固有の不健全経路（仮定 discharge）は SAT では発生しない（目的境界も最適性証明も無い）。コーパス -a も通過。ただし NoGood 有効性（穴なし区間＝矛盾ドメイン）の前提には bounds_only モードの size() 等の残余リスクがあり「確実」ではない。採るなら SAT 限定＋env ガードで soundness スイープが前提。
- **教訓**: NoGood に入れてよいのは decision（探索の仮定）であって、その伝播帰結（制約スコープ境界）ではない。境界を健全に取り込むにはフル LCG（reason 節→1-UIP resolution）が必要。
