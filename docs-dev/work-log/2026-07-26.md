- **ベンチ経路で native tree が無効になっていたことを発見**
  - CLAUDE.md 記載の `--solver sabori_csp`(名前解決)が `squashfs-root/usr/share/minizinc/solvers/sabori.msc` を掴み、その mznlib は古いスナップショットで `fzn_tree_int.mzn` / `fzn_subcircuit.mzn` / `fzn_lex_*` / `fzn_increasing_*` / `fzn_seq_precede_chain_int.mzn` / `fzn_value_precede*.mzn` を欠いていた

- **surface-based-tsp の実力を再計測**(build 側 msc、120秒、`-i` 付き)
  - burma14 / ulysses16 は OPT(3323 / 6900)
  - berlin52 8346、st70 806、ch130 8124 でいずれも S。同条件の chuffed は 8513 / 800 / 9040 で、berlin52・ch130 は sabori が上回る

  - `objective <= 8345`(自分の解より1だけ厳しい)を課すと60秒で解なし。`objective <= 0` でも30秒で UNSAT を証明できない(chuffed も同じ)
  - MZC2026 の全エントリー結果でも、最適性を証明できたのは cplex / gurobi / highs / scip の MIP 勢のみ。純CP(choco-cp / gecode / jacop / nucs / sicstus)は全て UNK で、LP 緩和が効くタイプの問題
- **anytime 曲線が15〜20秒で完全に停止することを600秒走行で確認**
  - berlin52: 15.45秒で 8346 到達後、残り585秒 改善ゼロ
  - ch130: 21.02秒で 8278 到達後、残り579秒 改善ゼロ
- **gprof + 自前計測で性能ボトルネックを特定**
  - `IntLinEqConstraint::propagate_lower_bounds` / `propagate_upper_bounds` が 58.4%(61.5M + 55.7M calls)
  - potential は差分更新されているのにフィルタリングループが毎回 O(n) 全走査で、slack による早期打ち切りがない
  - 30秒あたり berlin52 54.3M スキャン中 有効 3.4%、96.6% は `max|c_j|·span_j <= slack` で空振り確定。訪問項数は12.6億回(ch130 は23.7億回)

  - 閉路予防自体は機能している(berlin52 60秒で765万回呼び出し、65万回の閉路検出、106万辺の刈り込み)。コストは 7.4%(build_uf 4.4%)

**設計判断・理由**

- **ソルバー指定は名前解決をやめて `.msc` 絶対パス固定にした**。名前解決は「どの `.msc` を掴んだか」が出力に出ないため、mznlib の食い違いが黙って通る。今回の native tree 無効化がまさにそれで、半年単位で気づけない可能性があった。`sabori.msc` を削除して曖昧さの元を断ち、誤用時は黙って壊れるのではなく即エラーにした
- **`sabori_a.msc` / `sabori_b.msc` / `sabori_nogac.msc` は削除せず残した**。同じ古い mznlib を指しているが `name` が衝突せず、リポジトリ内から参照もない。README に「使わないこと」と明記するに留めた
- **性能改善(静的ガード)は今回コミットしなかった**。1.6x は確かに出たが目的値が1も動かず、この問題の律速ではないことが確定した。他問題への横展開で価値が出る可能性はあるので、パッチはセッションの scratchpad に退避
- **tree の増分連結性伝播は実装しない判断**。計測で「1つも刈れない」ことが確定したため。実装コストを払う先ではない
- **目的関数の下界強化も見送り**。濃度考慮 LB を入れても −19383 止まりで最適値 7542 に対して無意味。実効的な下界には LP 緩和が要るが、これは既存の立ち位置(LP/MIP は外部ポートフォリオ層、内製しない)と整合させるべき領域

## 2026-07-26 13:30〜16:00 subcircuit の効果検証・mznlib 汚染の根治・bisect 判定基準の検討

**作業ブランチ**: `feature/native-tree`（subcircuit の A/B のみ `feature/native-subcircuit` を worktree に切って実施）

**実施内容**

- **native subcircuit で orthorio が速くなったかを A/B で検証 → 速くなっていない**
  - `feature/native-subcircuit`(d7cf7cb) を worktree にビルドし、**同一バイナリで mznlib だけ差し替え**て比較(native = `fzn_subcircuit.mzn` あり / std = 削除して標準分解)
  - モデルは確かに縮む: challenge_01 で 3301→2794 vars、5920→5357 cons。5インスタンスとも同程度
  - しかし180秒×5インスタンス×2構成の全10ランで**解ゼロ**。fails 数の差は −11%〜+17% で方向が揃わず、`ng_prune` も ch01 で native 782 / std 6158 と逆転しており、いずれもノイズの範囲
  - chuffed は同じ challenge_01 を60秒以内に objective=44 で解くので、インスタンスも計測経路も健全。既存メモリの結論(LCG ギャップが本質)をクリーンな A/B で裏づけた形。ただし記録にあった「枝刈り強化(ng_prune 256→1904)」は今回の計測では再現しなかった
- **現ブランチに subcircuit 実装が無いこと、および build mznlib の汚染を発見**
  - `feature/native-tree` には `subcircuit.cpp` も registry 登録も無い(native subcircuit は別ブランチの成果)
  - にもかかわらず `build/share/minizinc/sabori_csp/` に他ブランチ由来の9ファイルが残留していた(`fzn_subcircuit` / `fzn_lex_less_*` / `fzn_lex_lesseq_*` / `fzn_seq_precede_chain_int` / `fzn_value_precede*` / `fzn_bin_packing_load`)
  - これらは `sabori_csp_subcircuit` / `sabori_lex_less` / `sabori_value_precede` / `sabori_bin_packing_load` を emit するが、現ブランチのバイナリは1つも実装していない(実装済みは `sabori_tree` のみ)。結果、**現ブランチで orthorio は解けないのではなく即 ERR** になっていた
  - 原因は cmake の差分コピー。`configure_file` で1ファイルずつ配るだけで消えたファイルを削除せず、`file(GLOB)` も configure 時に固定されるためファイルの増減に追従しない
  - `cmake/sync_mznlib.cmake` を追加し、出力先を毎回削除してから配置し直す方式へ変更。**ビルド毎に走る custom target** から呼ぶ
  - 2シナリオで検証: (A) build 側に他ブランチの `.mzn` を仕込んで**ビルドのみ**実行 → 自動削除される、(B) `share/` への追加/削除がビルドのみで build 側に反映される
- **orthorio の all_different は GAC に載らないことを確認**
  - `constraint_registry.cpp` の分岐は `ctx.use_gac || gac_favorable(vars)`。`gac_favorable` の閾値は変数数32以下・値域幅32以下
  - orthorio の2本(`next` と `X_INTRODUCED_606_`)はどちらも `array[1..55] of var 1..55` で、変数数・値域幅とも約1.7倍あり二重に外れる。トレースを仮設して `-> basic (use_gac=0 gac_favorable=0)` を実測確認
  - `-G` 強制で GAC にすると探索ノード数は 15〜25% 減るが(1ノードのコスト増)、**解は依然ゼロ**で結果は変わらない
- **bisect 判定を「範囲」から「残り値数」に変える案を検証 → 不採用**
  - 現行は `prev_max - prev_min + 1 > 閾値(8)`。穴あきドメインで両者が食い違う
  - まず発火余地を計測: 38問中22問で1%以上、tower 69.1% / black-hole 64.3% / stripboard 51.6% / accap 51.2% と高頻度で判定が反転する(no-op ではない)
  - A/B(2024・2025 の38問 × 3シード × 30秒、`SABORI_BISECT_COUNT` で切替)の結果は **net −16**(勝ち15 / 負け31 / 引き分け68)。3シードすべてで負け越し
  - 個別に見ると同じ30秒で回れるノード数が減っている(tower 1574→9289 fails、black-hole 11566→32061、accap 231640→429117)。穴あきでも区間で切れば1手で残り値の半分を落とせるのに、列挙だと1値ずつしか進まないため
  - 加えて bisect モードにしか無い勾配ヒント/ベスト解ヒントによる分岐方向選択が使われなくなる。fox-geese-corn が目的値 20→26 と負けたのはこの筋と思われる

**設計判断・理由**

- **subcircuit の検証は「同一バイナリ・mznlib 差し替え」にした**。ブランチ間でバイナリを変えると探索実装の差が交絡するため。native/std の切替を mznlib だけに閉じ込めることで、比較対象を伝播の強さに限定できる
- **mznlib 同期を configure 時ではなくビルド時にした**。最初は configure 時に `REMOVE_RECURSE` + `CONFIGURE_DEPENDS` を足す形で実装したが、検証したら再現シナリオを潰せていなかった。ブランチ切替の直後に打つのは普通 `cmake --build` だけで、`cmake -B build` を打ち直さないと同期が走らないため。**「直したつもり」で終わらせず再現シナリオで確かめたのが分かれ目だった**
- **bisect 判定基準の変更は不採用**。net −16 が3シードとも同方向で、統計的なブレではない。bisect を減らす方向自体が分が悪いと読める
- **all_different の GAC 閾値緩和には手を付けなかった**。orthorio を GAC に載せても `-G` の実測どおり解けない。subcircuit と同じ「伝播は強くなるが解けない」パターンになる公算が高い
