- **div/mod ペアの伝播穴を発見**。モデルの `x(n) = (n-1) mod W + 1` / `y(n) = (n-1) div W + 1` が
  `int_div(t,11,q)` + `int_mod(t,11,r)`（同一被除数・同一定数除数）に分解される。
  `IntModConstraint::on_set_min/max`（`src/core/constraints/arithmetic.cpp:1241`）は `propagate_bounds` を
  呼ぶだけで、余り側から被除数へは何も伝播しない。被除数のドメインを絞るのは
  「y と z が確定」の `on_instantiate` 分岐のみ。結果として
  `next[n]` の値削除が `nextx/nexty` へ返らず `sb[n]` に届かない（主要伝播経路が片方向で死んでいた）。
- **MiniZinc レベルの冗長制約で A/B 検証**。`constraint forall (n in 1..NODES) (next[n] == (nexty[n]-1)*WIDTH + nextx[n]);`
  を追加（`int_lin_eq` 154→209）。
  - 実インスタンス（challenge_01/03/04/12/13 × seed 1-3 × 120s、直接 fzn 実行）:
    **両者とも解ゼロ**。fails は全 15 ペアで channel 版が 10〜25% 少ないが、
    同一時間での fails 減はノード単価上昇と区別できず、この指標だけでは判定不能。
  - 自作の閉じる小インスタンス（3×5〜4×7、1〜3エージェント、seed 1-3、最適性証明まで）:
    **12ペア全勝**。fails 約 −40%、時間 約 −35%。
    最も明確なのは s4（4×7, 3agents, UNSAT 証明）で fails 48565/86628/58256 → 17966/32738/25479、
    10.4-13.0s → 5.7-8.5s。最適値は全ケース一致（s1=7 / s2=12 / s3=14）。
    **UNSAT 証明で勝っている＝枝刈りが実際に強くなっている**（ノードが遅くなっただけではない）。
- 目的関数の構造も FZN 上で確認: `set_in_reif(sb[n],1..2,b)` と `int_eq_reif(next[n],n,b)` が
  同じ b を共有し、`objective = 8 + Σ¬b`。つまり **objective ≡ subcircuit の頂点数**。

### 設計判断・理由

- **修正箇所は mznlib ではなく solver 側の presolve pass**にする。
  `int_div`/`int_mod` は FlatZinc builtin で redefinitions での上書きは筋が悪く、
  そもそも「div と mod の**ペア**」という関係は MiniZinc 側からは見えない。
  `OneHotChannelAggregator`（`src/core/solver.cpp:341`, Phase 1 presolve 後）と同じ位置に
  `DivModChannelAggregator` を置くのが素直。
- 被除数が非負・除数が正の定数なら `x = c*q + r ∧ 0 ≤ r < c` と div/mod は等価なので、
  **追加ではなく置換**できる（今回の実測は冗長追加なので、置換版はさらに良くなるはず）。
- **orthorio 自体は落ちない**。実インスタンスは依然 解ゼロで、
  [[orthorio-lcg-bound-subcircuit]] の「LCG が本質」という結論は変わらない。
  今回の抽出は orthorio 対策ではなく、grid indexing イディオム全般に効く一般改善として扱う。
- 目的関数 ≡ subcircuit 頂点数の抽出（cardinality 付き subcircuit + マーカー間最短路下界）は
  構造としては確認できたが、**初解が出ない現状では下界枝刈りが1回も効かない**ため優先度を下げる。

## 2026-07-29 01:00 `DivModChannelAggregator` 実装

### 実施内容

- `include/sabori_csp/divmod_channel_aggregator.hpp` / `src/core/divmod_channel_aggregator.cpp` を新規追加。
  `(x_id, 定数除数 c)` をキー（`std::map` で走査順を決定的に）に int_div / int_mod を突き合わせ、
  `c*q + r - x = 0` の `IntLinEqConstraint` を生成。あわせて `0 <= r < c` を明示的に課す。
  ガード: c > 0（定数）、x の下限 >= 0、q/r/x が互いに異なること。
- `IntDivConstraint` / `IntModConstraint` に `x_id()/y_id()/z_id()` アクセサ追加。
- `src/core/solver.cpp` の OneHot 集約直後に挿入。`SABORI_DIVMOD`（0=無効 / 1=追加（既定） / 2=置換）。
- テスト `tests/cpp/test_divmod_channel.cpp`（6 ケース、全解集合をブルートフォース照合）。
  ランダム fuzz 120 ケース（範囲・除数・追加制約をランダム、ON/OFF の全解集合比較）も mismatch 0。
- **ctest 270/270 pass**（golden master 含む。新規 6 ケース増）。

### 設計判断・理由

- **置換ではなく追加を既定にした**。当初は div/mod を消す設計にしたが 3-way A/B で判明:
  IntDiv/IntMod は「x % c != r となる値を x のドメインから落とす」**ドメイン**フィルタを持ち、
  線形制約の bounds 伝播はこれを代替できない。置換（mode2）は s2/s3 で off より悪化するケースあり。
  追加（mode1）は 12/12 で off に勝った。置換は健全ではあるので mode2 として残す。
- **集約が発火しないときは `build_constraint_watch_list()` を呼ばない**。
  無条件に呼ぶと div/mod を1本も持たないモデルでも watch 構造の内部順序が変わり探索軌道がずれた
  （carpet-cutting 等で検出）。**再構築は冪等ではない**ので、pass は「何もしないなら本当に何もしない」
  ことを保証する必要がある。

## 2026-07-29 02:30 置換モードを専用制約 `IntDivModChannel` に置き換え

**きっかけ（ユーザ指摘）**: 「置換するなら int_div / int_mod の処理を代替すればよい。
伝播の処理が減るし activity の変化も変わる」。線形1本で置換すると div/mod のドメイン
フィルタが落ちるのが問題だったので、**そのフィルタを内包した専用制約を作れば
置換が成立する**という筋。

### 実施内容

- `IntDivModChannelConstraint(x, c, q, r)` を新規実装（`src/core/constraints/int_divmod_channel.cpp`）。
  x >= 0 / c > 0 では (q,r) ↔ x が全単射なので、D(x) を1回走査するだけで
  **三項関係の GAC** が取れる（各 v について v/c ∈ D(q) かつ v%c ∈ D(r) を検査し、
  同時に q/r 側の支持を集めて支持なしを落とす）。div/mod/線形をこの1本で置換。
- `SABORI_DIVMOD` を 4 値に: 0=無効 / 1=線形追加（div/mod 残す） /
  2=専用制約（値走査は穴が生じるイベントのみ） / **3=専用制約＋全イベント値走査（既定）**。
- fuzz 150 ケース × 全モードで全解集合一致、ctest 270/270 pass。

### 計測（s3/s4、8 シード、**CPU 時間**）

| | s3 cpu | s3 fails | s4 cpu | s4 fails |
|---|---|---|---|---|
| 0 off | 50.9 | 75500 | 177.3 | 541449 |
| 1 augment | 38.4 | 47362 | 127.5 | 224044 |
| 2 native(走査制限) | 44.7 | 63500 | 136.2 | 275298 |
| 3 native+全走査 | **38.2** | **46474** | **122.9** | **196433** |

指摘どおり、**伝播器 3 本 → 1 本にした分で GAC のコストが吸収され**、
fails・CPU 時間ともに最良になった。既定を 3 に変更。

### 設計判断・理由

- **値走査の制限（mode 2）は失敗**。「走査は O(|D(x)|) だからイベントを絞る」と考えて
  bounds イベントで走査を止めたが、失う枝刈りのほうが大きく fails +37%（s3）/+40%（s4）。
  ablation として残すが既定にはしない。
- **壁時計時間で A/B してはいけない**。並列実行数が違うだけで s3 mode1 が 43.3s→58.0s と
  35% ぶれた（fails は決定的で完全一致）。`/usr/bin/time -f "%U"` の CPU 時間に切り替えて
  ようやく mode 間の差が読めた。
- **未解インスタンスの fails 比較は throughput を見ているだけ**。rotating-workforce の
  UNK 群は mode2 で fails が 20〜55% 減ったが、これは1ノードが遅くなった signal であって
  枝刈りではない。走査制限を入れたら同じ instance の fails が 11131 → 200053 に跳ねた。

### 残る懸念

- rotating-workforce の唯一解ける Example1242（6 シード CPU 合計）は
  off 51.7 / augment 20.9 / native+走査 31.6 で **augment が最良**。
  Example103 は三者同着。s3/s4 と逆向きで、mode1 と mode3 の差は現サンプルではノイズ帯。
  既定を 3 にしたのは「伝播器が減る・GAC で原理的に強い・4 ターゲット中 3 で最良」という
  総合判断であって、統計的に分離できてはいない。より広いゲートが要る。
- mode3 は IntDiv/IntMod を**モデルから外す**ので、新制約のバグがそのまま健全性事故になる。
  fuzz 150×全モード / 単体 6 ケース / golden master は通っている。
