## 2026-07-29 01:00 `DivModChannelAggregator` 実装

### 設計判断・理由

- **置換ではなく追加を既定にした**。当初は div/mod を消す設計にしたが 3-way A/B で判明:
  IntDiv/IntMod は「x % c != r となる値を x のドメインから落とす」**ドメイン**フィルタを持ち、
  線形制約の bounds 伝播はこれを代替できない。置換（mode2）は s2/s3 で off より悪化するケースあり。
  追加（mode1）は 12/12 で off に勝った。置換は健全ではあるので mode2 として残す。

  無条件に呼ぶと div/mod を1本も持たないモデルでも watch 構造の内部順序が変わり探索軌道がずれた
  （carpet-cutting 等で検出）。**再構築は冪等ではない**ので、pass は「何もしないなら本当に何もしない」
  ことを保証する必要がある。

## 2026-07-29 02:30 置換モードを専用制約 `IntDivModChannel` に置き換え

**きっかけ（ユーザ指摘）**: 「置換するなら int_div / int_mod の処理を代替すればよい。
伝播の処理が減るし activity の変化も変わる」。線形1本で置換すると div/mod のドメイン
フィルタが落ちるのが問題だったので、**そのフィルタを内包した専用制約を作れば
置換が成立する**という筋。

### 実施内容

- `IntDivModChannelConstraint(x, c, q, r)` を新規実装（`src/core/constraints/int_divmod_channel.cpp`）。
  x >= 0 / c > 0 では (q,r) ↔ x が全単射なので、D(x) を1回走査するだけで
  **三項関係の GAC** が取れる（各 v について v/c ∈ D(q) かつ v%c ∈ D(r) を検査し、
  同時に q/r 側の支持を集めて支持なしを落とす）。div/mod/線形をこの1本で置換。
- `SABORI_DIVMOD` を 4 値に: 0=無効 / 1=線形追加（div/mod 残す） /
  2=専用制約（値走査は穴が生じるイベントのみ） / **3=専用制約＋全イベント値走査（既定）**。
- fuzz 150 ケース × 全モードで全解集合一致、ctest 270/270 pass。

### 計測（s3/s4、8 シード、**CPU 時間**）

| | s3 cpu | s3 fails | s4 cpu | s4 fails |
|---|---|---|---|---|
| 0 off | 50.9 | 75500 | 177.3 | 541449 |
| 1 augment | 38.4 | 47362 | 127.5 | 224044 |
| 2 native(走査制限) | 44.7 | 63500 | 136.2 | 275298 |
| 3 native+全走査 | **38.2** | **46474** | **122.9** | **196433** |

指摘どおり、**伝播器 3 本 → 1 本にした分で GAC のコストが吸収され**、
fails・CPU 時間ともに最良になった。既定を 3 に変更。

### 設計判断・理由

- **値走査の制限（mode 2）は失敗**。「走査は O(|D(x)|) だからイベントを絞る」と考えて
  bounds イベントで走査を止めたが、失う枝刈りのほうが大きく fails +37%（s3）/+40%（s4）。
  ablation として残すが既定にはしない。
- **壁時計時間で A/B してはいけない**。並列実行数が違うだけで s3 mode1 が 43.3s→58.0s と
  35% ぶれた（fails は決定的で完全一致）。`/usr/bin/time -f "%U"` の CPU 時間に切り替えて
  ようやく mode 間の差が読めた。
- **未解インスタンスの fails 比較は throughput を見ているだけ**。rotating-workforce の
  UNK 群は mode2 で fails が 20〜55% 減ったが、これは1ノードが遅くなった signal であって
  枝刈りではない。走査制限を入れたら同じ instance の fails が 11131 → 200053 に跳ねた。

### 残る懸念

- rotating-workforce の唯一解ける Example1242（6 シード CPU 合計）は
  off 51.7 / augment 20.9 / native+走査 31.6 で **augment が最良**。
  Example103 は三者同着。s3/s4 と逆向きで、mode1 と mode3 の差は現サンプルではノイズ帯。
  既定を 3 にしたのは「伝播器が減る・GAC で原理的に強い・4 ターゲット中 3 で最良」という
  総合判断であって、統計的に分離できてはいない。より広いゲートが要る。
- mode3 は IntDiv/IntMod を**モデルから外す**ので、新制約のバグがそのまま健全性事故になる。
  fuzz 150×全モード / 単体 6 ケース / golden master は通っている。

## 2026-07-29 04:30 phase 忘却（SABORI_PHASE_FORGET）の実験コードを撤去

**判断: 筋がよくなかったので、作業ログだけ残してコードは削除。** 未コミットのまま

### 何を試したか

phase saving の「保存値をどう使うか」ではなく **「保存値そのものを、証拠のある場所で忘れる」**
という方向。矛盾を起こした制約に紐づく変数から一様に1つ選び、保存 phase を消す:

- `Solver::forget_phase_on_conflict(model, constraint_idx)` を伝播失敗の 2 箇所から呼ぶ
  （制約の変数配列から `rng_() % vids.size()` で 1 つ選ぶだけの O(1)、ホットパスを汚さない）
- `SABORI_PHASE_FORGET` の 4 モード:
  - `1`      = 制約の全変数から選び、`current_best_assignment_` と供給源 `best_assignment_` の両方を消す
  - `cur`    = 全変数から選び、current のみ（リスタートで復活する）
  - `dec`    = **決定変数に限定**し、current のみ
  - `decsrc` = 決定変数に限定し、両方
- `dec` 系のために `decision_mark_`（decision_trail_ 上の変数の出現数カウンタ。bisect は
  同一変数を複数回決定しうるので bool ではなくカウンタ）と候補収集バッファ `forget_cand_` を追加。
  decision_trail_ の push/pop 4 箇所で増減させる必要があった。

**動機**: 解の無い探索では phase 供給源が「最深の行き詰まり」に凍結され、毎リスタート
再インストールされる（＝既知の失敗を再生し続ける）。矛盾に実際に関与した制約の変数だけを
忘れれば、悪い部分を証拠のある場所で捨てつつ無関係な部分は温存できる、という筋。

### 結果と、撤去した理由

- **全変数版（`1` / `cur`）は 8 シード A/B で net −48 / −18 と明確に悪化。**
  矛盾は探索のいたるところで起きるため、「証拠のある箇所を狙う」つもりが実際には
  無差別破壊になっていた。伝播で決まった値は「選択」ではないので、消しても実際に
  含意されていた情報を壊すだけ。
- `dec` / `decsrc`（決定変数限定）はその反省から実装したが、**本セッションでは計測していない**。
  効果不明のまま、decision_trail_ の push/pop 4 箇所に副作用カウンタを持ち込むコストだけが
  確実に残る形になっていた。
- 既定 OFF の実験フラグとはいえ、`decision_mark_` の増減は探索のホットパス（bisect /
  enumerate / probe / ascent）に散らばる。効果が測れていない施策のために、
  そこへ状態を1つ増やしたまま置いておく価値はないと判断した。

## 2026-07-29 08:00 「解ゼロ」の原因切り分け（経路構造 vs 時間・容量）

### 失敗した切り分け 2 つ（記録として）

1. **目的関数を外して satisfy にする** → 無効。
   - yumi は `period`（目的変数）が**スケジュール地平線を兼ねている**ため、目的を外すと
     問題の性質が変わる。satisfy 版は **CP-SAT でも解けなくなった**。
   - vrp-submission は satisfy 版で sabori が解を出したが、中身は `objective = 13375`
     （CP-SAT は 415）、`departureTime` が 14 万台。**時間変数が野放しになりゴミ解が
     自明に取れるだけ**で、経路が簡単だという証拠にならない。
2. **既知の実行可能値で目的変数に上限を課して satisfy** → 無効。

**教訓**: 目的変数が地平線や資源上限を兼ねているモデルでは、目的を外す/固定する系の

## 2026-07-29 09:30 フロー緩和の前提を検証 → 撤回、yumi の真のボトルネックを特定

実装に入る前に前提を確認したところ、**フロー緩和の設計自体が筋悪**と分かったので撤回した。

### 前提の否定: フロー緩和は alldifferent GAC に吸収される

既存の到達可能性フィルタ（`filter_reachability`, `SABORI_SUBCIRCUIT_REACH`）の実装を
読んで気づいた: 「断片を頂点素なパスで結べるか」を容量1のフローで見るというのは、
縮約グラフ上で「各断片の入次数・出次数が1、自由ノードは高々1回使用」を課すこと、
つまり**割当（マッチング）問題**であって、`alldifferent(next)` の GAC が与える情報と
ほぼ同じ。フローが到達可能性より強いのは事実だが、強くなった分を既に別の制約が
持っているなら意味がない。

標的 5 インスタンスで実測（120s、def / -G / REACH / -G+REACH）:

| instance | def | -G(GAC) | REACH | -G+REACH |
|---|---|---|---|---|
| orthorio ch01 | 0解 512711 | 0解 446174 | 0解 567884 | 0解 429426 |
| orthorio ch03 | 0解 484123 | 0解 378801 | 0解 483816 | 0解 371924 |
| orthorio ch04 | **1解** 465277 | 0解 392689 | 0解 498119 | 0解 367563 |
| yumi22 p_8 | 0解 1565 | 0解 1617 | 0解 1561 | 0解 1638 |
| yumi23 p_9 | 0解 8034 | 0解 2874 | 0解 8047 | 0解 2005 |

GAC は fails を 10〜65% 減らすが **解は 1 つも増えない**。到達可能性フィルタは
ほぼ無効（メモリの記録どおり）。**頂点素性の情報は不足していない**ので、
それを強める方向のフロー緩和は投資に見合わない。

副産物: **orthorio challenge_04 で既定構成が解を発見**（従来ゼロ）。div/mod チャネルの効果。

### yumi の真のボトルネックは伝播の不動点収束

上表の yumi の fails に注目: **120 秒で 1565 fails = 13 ノード/秒**。
枝刈りの問題ではなく 1 ノードのコストの問題。制約種別ごとの統計（60 秒）:

```
yumi22_p8                    Calls    Reductions  Fails
  array_var_int_element  835344430    412218005     372
  int_lin_eq             147687489     65826890     834
  int_max                 84839619     39743736       0
（参考）orthorio ch01
  int_eq_reif            429405015    150842563       6   ← ノード数は 250k 超
```

1 ノードあたり **element 呼び出し 55 万回・ドメイン削減 27.5 万回**。
変数 10491 個に対して削減 27.5 万回ということは、各変数の境界が 1 ノードで平均 27 回
更新されている＝**境界が少しずつしか動かない緩慢な収束**。
実際 yumi22_p8 には**幅 5686 のドメインを持つ変数が 232 個**あり（`arrival_time` 系）、
41 タスクの時間連鎖を `array_var_int_element`（`location[successor[t]]`）と
`int_lin_eq` / `int_max` が相互に起こし合っている。

経路を固定すると OPTIMAL まで解けるのは、固定によりこの連鎖が一気に確定するため。
「経路探索がボトルネック」という前節の判定は正しいが、**理由は経路の伝播が弱いからでなく、
経路が未確定な間は 1 ノードが極端に高価だから**。

`pending_updates_` は既に FIFO（読み出しインデックス方式）なので、キュー順序の
単純な入れ替えという安直な手は無い。

### 結論と次の候補

- **フロー緩和は実装しない**。頂点素性は既に足りており、alldifferent GAC で代替可能で、
  かつそれでも解は増えない。
- orthorio は引き続き LCG ギャップ（[[orthorio-lcg-bound-subcircuit]] の結論は不変）。
- **yumi 系の次の一手は伝播の収束改善**。候補:
  1. 伝播キューの優先度付け（安価な制約を先に不動点まで回し、element/線形の連鎖は後回し）
  2. 時間連鎖専用の伝播器（カオス反復でなくトポロジカル順の1回掃引）
  3. 1 ノードあたりの伝播回数上限（枝刈りとスループットのトレードオフ）。
     ただし葉での健全性（不動点前に解と誤認しないか）に注意が要る。

## 2026-07-29 11:00 トポロジカル順は不成立 → element の support tracking 閾値が真因

「時間連鎖をトポロジカル順に1回掃引する」案を検討したが、**連鎖の要が
`next_arrival_time[t] = arrival_time[successor[t]]` で添字が決定変数**のため、
経路が未確定な間は静的なトポロジカル順が存在しない。`task[]` 側で見ても
`task[t+1] = successor[task[t]]` で同じく変数添字。案としては不成立。

### 代わりに測ったこと: element を起こしているのは添字か値か

`ArrayVarIntElementConstraint` の各コールバックに一時的な計数を入れて内訳を取った
（計測後に撤去）。var_ids_ は [0]=index, [1]=result, [2..]=array。

| model (60s) | index | result | array |
|---|---|---|---|
| yumi22 p_8 | 571,448 (0.04%) | 32.8M (2.5%) | **1,288,356,217 (97.5%)** |
| yumi23 p_9 | 1,142,985 (0.09%) | 35.4M (2.9%) | **1,203,800,904 (97.0%)** |
| orthorio ch01 | 66.7M (11.9%) | 18.8M (3.4%) | 477M (84.7%) |

**配列要素側が 97.5%**。element は配列全体を watch するので、`arrival_time[j]` の
どの境界更新も、その配列を含む全 element を起こす（n 個の element × n 個の配列変数）。

### 真因: support tracking が幅の広いドメインで無効化されていた

`array_var_int_element.cpp:197` の `use_support_tracking_ = (total_dom / n_ <= 4)`。
yumi の `arrival_time` は幅 5686 なので**無効**になり、13 億回の配列側起床が
毎回 `propagate_via_queue` の全スキャンに落ちていた。
support tracking が有効なら「現在の support でない要素の変化」は index フィルタだけで
早期 return できる（起床の約 1 - 1/n がこれに当たる）。

閾値を `SABORI_ELEM_SUPPORT` で可変にして計測:

| instance | thr=4 (従来) | thr=常時有効 | 倍率 |
|---|---|---|---|
| yumi22 p_8 (120s) | 1573 fails | 10272 fails | **6.5x** |
| yumi23 p_9 (120s) | 7510 fails | 109092 fails | **14.5x** |
| yumi22 p_8 (600s) | 9733 | 193327 | 20x |
| yumi23 p_9 (600s) | 72965 | 417382 | 5.7x |

**ただし yumi は 600s でも解ゼロ**。スループットだけでは届かない。

### ゲート（array_var_int_element を 20 本超持つ 59 モデル、60s）

- ステータス階層: **正味 +3**（UNK→SAT 1 / SAT→OPT 3 / OPT→SAT 1）
  - 勝: 2025 tsptw (SAT→OPT), 2017 tdtsp (SAT 9055→OPT 9055),
    2018 seat-moving (SAT 462→OPT 376), 2020 code-generator (UNK→SAT 89191)
  - 負: 2023 code-generator (OPT 6340→SAT 7898)
- 目的値: 勝ち 10・負け 6（最適化方向を .mzn から確認して判定）
- スループット: 速い 28 / 同等 20 / 遅い 11

**fails が一致しないので純粋な高速化ではない**。support モードは非 support 要素の
変化時に index フィルタしか行わないぶん枝刈りが弱く、速度との**トレードオフ**。
それでもステータス階層で正味 +3 なので**既定を「常時有効」に変更**した。
`SABORI_ELEM_SUPPORT=4` で従来動作に戻せる。

検証: ctest 270/270、golden 245/245 ALL GREEN（既定・従来動作の両方）。

## 2026-07-29 13:00 element support tracking の「悪くなった側」の分析

前節でトレードオフと片付けた負け（目的値 6 件・階層後退 1 件）を分析した。

### まず軌道差か枝刈り落ちかを切り分けた

`SABORI_FIX_MIXP=0 SABORI_BUMP_MODE=0` で変数選択を activity から切り離し、
**終了するモデル**（fails が決定的）で比較:

| model | thr=4 | thr=常時有効 |
|---|---|---|
| 2012 tpp | 6062 | 6500 |
| 2012 project-planning | 2107 | 2577 |
| 2024 compression | 14891 | 16115 |
| 2025 stripboard | **424** | **66962** |
| 2015 gfd-schedule | 4 | 9 |

**5 モデルすべてで thr=4 が少ない**。activity 経由の軌道差ではなく、本物の枝刈り落ち。

### 原因: result が締まったときの arr[index] への落とし込みが飛んでいた

`propagate_via_queue`（全スキャン）の末尾には「index が確定していれば
arr[index] と result を相互に締める」ブロックがある。support tracking の早期 return
経路（`internal_var_idx == 1` の result 分岐、および非 support 配列要素の分岐）は
`filter_index_against_result` だけを呼んで**このブロックを飛ばしていた**。
その結果「index は確定済みで、他制約が result を締めても arr[index] に伝わらない」
という欠落が生じる。

`sync_selected_element()` に切り出し、全スキャン末尾と3つの早期 return 経路から呼ぶよう修正
（フィルタの純増で、飛ばす経路は増えない）。

修正後（同じく activity 切り離し・決定的）:

| model | thr=4 | 修正前 | 修正後 |
|---|---|---|---|
| 2012 project-planning | 2107 | 2577 | **2107（一致）** |
| 2015 gfd-schedule | 4 | 9 | **4（一致）** |
| 2024 compression | 14891 | 16115 | **14136（thr=4 より良い）** |
| 2012 tpp | 6062 | 6500 | 7468（悪化のまま） |
| 2025 stripboard | 424 | 66962 | 16045（**38 倍差が残る**） |

2 件は完全一致まで回復、1 件は逆転。**stripboard の差は再現性がある本物の残存欠落**
（2 回実行して 424 / 16045 が完全一致）。原因は未特定。

### ゲート再実行（59 モデル、60s）

ステータス階層は **正味 +3、階層後退なし**:
- SAT→OPT: 2017 tdtsp / 2019 stochastic-vrp
- UNK→SAT: 2023 code-generator

### 重要な訂正: 60s のゲート行は再現しない

再実行で**基準線（thr=4）自体が動いた**行が複数ある
（2023 code-generator は OPT 6340 → UNK、2021 seat-moving は 1226 → 738）。
確認のため同一設定を 2 回走らせると **OPT と TIMEOUT に振れた**。

→ **前節の「目的値 勝ち 10・負け 6」は信用できない数字だった**。タイムアウトで

(a) 終了するモデルの fails（完全再現）と (b) ステータス階層の変化のうち再現するもの。
[[bench_circuit_volatility]] の「マージナル行はノイズで反転」と同じ罠を踏んでいた。

## 2026-07-29 15:00 stripboard の残存差の調査 → 枝刈り欠落ではなく軌道分岐

前節で「stripboard に 38 倍の残存欠落（424 vs 16045）、原因未特定」と書いた件を追った。
**結論: 残存する枝刈り欠落は無い。** 差はインクリメンタル伝播のイベント順序に起因する
軌道分岐だった。

### 決定的な証拠: 不動点で全スキャンしても何も変わらない

`propagate_batch` を実装し、fast path が近似した経路でバッチにスケジュールして
**イベントキューが空になった時点で全スキャンを1回**走らせた
（`schedule_constraint_batch` / `pop_scheduled_constraint` の既存機構）。

バッチは実際に走っている（デバッグ計数で 100 万回超）。にもかかわらず
**fails が 16045 のまま 1 ビットも変わらなかった**。取りこぼしがあればバッチが
拾って数値が動くはずなので、fast path は既に全スキャンと同じ不動点に達している。
→ 効果ゼロでコストだけ増えるのでバッチ機構は撤去した（`git checkout` で d1cc9f2 に復帰）。

### 残差の符号は設定で反転する

| 設定 | 2025 stripboard | 2012 tpp | 2024 compression |
|---|---|---|---|
| activity 切り離しのみ | 424 / **16045** | 6062 / **7468** | **14891** / 14136 |
| + 固定リスタート(luby:100) | 53353 / **155924** | **6863** / 4504 | **14223** / 14095 |
| + NoGood 学習無効(-N) | **175200** / 41841 | 8914 / **21439** | **35535** / 27329 |

（太字が悪い側。thr=4 / support の順）

**同じモデルで符号が3通りに割れる**。系統的な枝刈り劣位ではありえない。

### なぜ不動点が同じでも差が出るのか

sabori の伝播器は**内部状態を持つインクリメンタル実装**（support キャッシュ、
watched literal など）で、ドメイン状態の純関数ではない。したがって
イベント順序が変わると到達する不動点そのものは同じでも、
- enqueue されるイベントの個数と順序
- それに乗って動く NoGood 学習（経路依存）
- リスタート統計（reduction_count など）

が変わり、探索軌道が分岐する。単調伝播だから不動点は一意、という理屈は
「各伝播器がドメインの純関数である」場合にしか使えない。

### 前節の記述の訂正

前コミット（d1cc9f2）のメッセージに「stripboard の残存差は本物の残存欠落。原因は未特定」
と書いたが、**これは誤り**。再現性があること（424/16045 が 2 回一致）は
「決定的である」ことを示すだけで、「枝刈りが弱い」ことは示していない。
決定的な差と系統的な劣位を混同していた。

## 2026-07-29 17:00 vrp-submission の調査 → 伝播の欠陥は無かった（前節の訂正）

前節で「vrp-submission D_3v は経路を CP-SAT の最適解に固定してもなお解けない。
残るのは時間窓・積載の再帰だけなので、そこの伝播が効いていない」と書いた。**これは誤り。**

### 事実

fzn を直接実行すると普通に解ける:
- 経路固定モデル: **objective = 410**（CP-SAT の最適値と一致）
- 元モデル（経路も探索）: 55 秒で **194 解**、best objective 593〜625

一方 minizinc 経由だと 60 秒で 0 解、180 秒で 95 解（objective 770）。同じモデルで
直接実行のほうが圧倒的に良い。

### 原因: `--output-objective` が変数消去を阻害する

ベンチ（bench_circuit.py と今回の bench_routing.py）は `--output-objective` を付けている。
これを付けて flatten すると、このモデルでは **変数が 473 → 533 に増える**
（出力指定された変数は ModelSimplifier が消去できない）。同じ 55 秒で:

| fzn | vars | sols |
|---|---|---|
| 通常 | 473 | **194** |
| `--output-objective` 付き | 533 | **0** |

`-E`（変数消去を無効化）を通常 fzn に掛けても **0 解**。
→ このモデルの性能は変数消去に完全に依存しており、
**消去できない変数が 60 本増えるだけで 194 解 → 0 解に崩れる**。

### 影響範囲は限定的

他モデルで `--output-objective` の有無を比較したところ変数数は変わらなかった:

| model | 通常 | --output-objective |
|---|---|---|
| vrplc9_5_15 | 403 vars, 6 sols | 403 vars, 6 sols |
| yumi-static p_4 | 2535 vars, 11 sols | 2535 vars, 14 sols |
| cvrp A-n38-k5 | 505 vars, 39 sols | 505 vars, 39 sols |

vrp-submission は objective を定義する線形の連鎖がたまたま消去可能で、
`_objective` を出力に固定するとその連鎖が止まる、という特殊事情。
→ **routing 調査全体が汚染されているわけではない。誤分類は vrp-submission D_3v の 1 件のみ。**

### 結論

- **vrp-submission に伝播の欠陥は無い。**「経路側フィルタの標的は orthorio + yumi」
  という結論は変わらない（vrp は元々 fix-route probe で除外していた）。
- 代わりに **変数消去への脆さ**という別の観測が得られた。473 変数のモデルで
  60 本消去できないだけで解が出なくなるのは、探索・伝播のどこかが変数数に対して
  急激に劣化していることを示す。これは独立した調査項目。

## 2026-07-29 19:00 「60本消去できないと解が出ない」の調査 → 前節をさらに訂正

### 判明したこと（構造の事実）

- 増えた 60 本は **どの制約にも一度も現れない自由変数**（59 本が幅 460585 の
  `departureTime` 系 + `start_load`）。制約集合は完全に同一（567 本）。
- 原因フラグは `--output-objective` ではなく **`--output-mode dzn`**
  （473 vars / 473 vars / 533 vars / 533 vars for なし / --output-objective /
  --output-mode dzn / 両方）。前節の帰属は誤り。
- sabori は自由変数を認識していて `VariableSelector::build_order` で探索順の
  最後尾に置いている（`unconstrained_vars`）。

### しかし「194 解 → 0 解」は再現しなかった

5 シードで測り直すと崩れた（55 秒、improving solution の数）:

| | seed1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 通常 (473 vars) | 56 | 103 | 224 | 197 | 240 |
| `--output-mode dzn` (533 vars) | 40 | 88 | 39 | **0** | 61 |
| `-E`（変数消去 無効） | **0** | 62 | 70 | 65 | 91 |

**0 解は特定シードの当たり外れ**で、4/5 のシードでは解が出る。
前節の「消去できない変数が 60 本増えるだけで 194 解 → 0 解に崩れる」は誤り。

残る効果は穏当なもの:
- 変数消去は有効（56-240 対 0-91 で、おおむね 2 倍程度の改善解数）
- 自由変数 60 本の追加はやや不利（56-240 → 39-88）

いずれも「探索が急激に劣化する」ような話ではない。**独立した調査項目として挙げた
「変数消去への脆さ」は取り下げる。**

### 試して失敗した修正（差し戻し済み）

「自由変数は presolve で min に固定すれば済む」と考えて実装したが、

### 本セッション 4 度目の同じ誤り

単一実行の結果から系統差を結論する誤りを、このセッションで 4 回犯した:
