### 実施内容

#### 1. 依頼の前提を測定で訂正した

「`CumulativeConstraint::bump_activity` を速くしたい」という依頼だったので gprof
（`-pg -O2`、クリーンビルド、各20秒）で先に測ったところ、**ホットパスではなかった**。

| モデル | 総サンプル | bump_activity | 呼び出し |
|---|---|---|---|
| 2014__cyclic-rcpsp | 8.2s | 0.49% | 16,040 |
| 2014__smelt | 0.76s | 1.32% | 43,098 |
| 2016__gfd-schedule | — | 0.00% | **3** |
| 2024__yumi-dynamic | — | 0.00% | **4** |
| 他4モデル | 8〜19s | 0.00% | 11〜71 |

`bump_activity` は `record_constraint_call` から**矛盾を検出した制約に対してのみ**
呼ばれる。矛盾の大半は `IntLinLeImp` と NoGood 側で出ており、cumulative の伝播器は
矛盾より前に刈っているため、呼び出し自体が少ない。ゼロ秒にしても最大 0.5%。

実際に時間を使っていたのは TTEF（forward 7.04% + backward 6.46% + energy_up_to 1.88%）
だったので、ユーザ合意のうえ対象を切り替えた。

#### 2. TTEF: theta_cp が実は前置和だった（`cc6a444` で main にマージ）

両パスの内側ループは Theta 内の各タスクについて
`req_i * max(0, min(ect_i,R) - max(lst_i,L))` を毎 k 再計算していたが、
**この clip は恒等変換**だった。`build_tasks` より `ect = est+dur`、`lct = lst+dur`、
`est <= lst` なので `ect <= lct`。forward（lct 昇順）では `i <= k` について
`lct_i <= R` かつ `ect_i <= lct_i` で上側の min が外れ、`est_i >= L` かつ
`lst_i >= est_i` で下側の max も外れる。backward（est 降順）も対称。

よって寄与は L,R に依存しないタスク固有の mandatory エネルギーで、`energy_theta` と
同じ running 前置和にできる。内側 O(k) ループが消えて **O(n^2) → O(n log n)**。

あわせて energy_up_to のカーソル化（両パスとも L は単調非増加・R は単調非減少なので
二分探索を片方向移動に置換、償却 O(1)）、j ループの O(1) スキップ判定、
スクラッチのメンバ化。

計測: forward 0.60s → 0.06s、backward 0.55s → 0.11s、energy_up_to 0.16s → 0.10s。
wall-clock は `2014__smelt` が fails 完全一致で約 −20%（1.4→1.1s）、
`2014__cyclic-rcpsp` が同時間で fails 1.10〜1.21 倍（seed1 は SOL → **OPTIMAL**）。

#### 3. init_activity の検討（不採用）

「bump_activity を工夫して早期に解を見つけられないか」という問いに対し、
**射程の広さから init_activity を選んだ**。bump は gfd-schedule で3回・yumi で4回
しか呼ばれないが、init_activity は探索開始時に必ず呼ばれる。そして他の 9 制約が
実装している中で cumulative だけ未実装だった。

窓 `w = lct - est`、`tightness = dur / w` として 4 モード + 対照 2 モードを実装し、
**初解到達時刻**を主指標にしたハーネス（`bench_cumul_init.py`）で 38 モデル ×
3 シード × 30 秒を計測。

| mode | 初解を得た/失った | 初解時刻 速い/遅い | 目的値 良い/悪い |
|---|---|---|---|
| 2 (tightness×req/cap) | **5 / 0** | 27 / 31 | **9 / 6** |
| 5 (反転・対照) | 3 / 0 | 25 / 32 | 6 / 12 |
| 6 (一律・対照) | 1 / 0 | 25 / 37 | 7 / 10 |

mode2 は対照を上回り、`2023__code-generator` は 2 ラウンド合計で mode0 が 0/6、
mode2 が 6/6 と再現した。しかし効果が出るのは code-generator 2 問だけで、
残り 36 モデルは互角。反転・一律でも解が出るセルがあり、摂動成分が混ざっている。

**ユーザ判断で不採用**。2 モデルの反転で既定を変える根拠にはならない。

### 設計判断・理由

- **依頼をそのまま実装せず、先に profile を取った**。結果として対象が変わった。
  「速くしてほしい」と言われた関数が実際には 0.5% で、隣の TTEF が 13.5% だった
- **theta_cp の恒等性は「読んで気づく」類のもの**だった。`build_tasks` の
  `ect = est+dur` / `lct = lst+dur` と、両パスの走査順（lct 昇順 / est 降順）が
  与える単調性を突き合わせて初めて見える。プロファイラは「ここが重い」までしか言わない

- **init_activity の評価指標を fails から初解到達時刻へ変えた**。軌道が変わる変更では
  fails の比較は意味を失う。`-a` で逐次出力を読んで最初の `----------` の時刻を取る
  ハーネスを新設した
- **反転対照と一律対照を置いた**。これが判断を決めた。mode2 単独なら
  「5 セルで未解→解、逆方向ゼロ」で採用に見えるが、反転でも 3 セル取れるので
  摂動成分が分離できた

## 2026-09-20 07:10 〜 08:40 大型グローバル制約の無駄処理 監査

**作業ブランチ**: `perf/global-constraint-audit`（main から分岐、**未マージ**）

### 実施内容

実装サイズ順（comparison 1695 / logical 1508 / arithmetic 1462 / disjunctive 1063 /
cumulative 852 / count_eq 847 / int_lin_eq 761 / table 692 ...）に、
gprof（8 モデル）と静的読みを併用して「イベントごとに無駄な処理をしていないか」を見た。

#### 見つけた構造的な無駄: diffn の per-event 全ペア走査（`585d6e0` で修正）

`DiffnConstraint` の `on_set_min` / `on_set_max` / `on_instantiate` が、どの変数が
変化したかを**無視して**（引数が `/*internal_var_idx*/` とコメントアウトされていた）
毎回 n(n-1)/2 の全ペアを走査していた。矩形 r の変化が影響するのはペア (r, *) だけ。

不動点は変わらない。ペア (j,k)（r を含まない）は j か k が最後に変化した時点で
走査済みで、その後 bounds が動いていないなら新しい伝播は出ない。各変数の変化は
必ず自分のコールバックを呼ぶのでカバレッジも落ちない。

- gprof: `diffn_pairwise` 41.90%（5.12s, 2023__code-generator 15秒）が消滅
- wall-clock A/B（20秒 x 3シード）: 2023__code-generator 2.24/5.49/3.98 倍、
  2019__code-generator 4.63/5.19/3.71 倍（seed3 は UNKNOWN -> SOL）、
  stripboard 1.06/1.33/1.29 倍、合計 **2.08 倍**
- 軌道不変（golden 270/270、rectangle-packing で fails 完全一致）

#### 他の大型制約は問題なし

| 方式 | 制約 |
|---|---|
| batch スケジューリング（イベントを溜めて1回伝播） | all_different / disjunctive / regular / global_cardinality / value_precede / lex_lesseq / bin_packing_load |
| index を使った増分更新 | count_eq / table / int_one_hot_channel / nvalue / array_var_int_element / int_lin_le / int_lin_eq |

`internal_var_idx` を無視しているコールバックは 20 箇所あるが、**batch 方式なら無視は
正しい**（イベントが合流するため）。diffn だけが「無視したうえで per-event 全走査」だった。
`sync_selected_element`（8190 万回）も本体 O(1)・5ns/回で、構造的な無駄ではなく呼び出し量。

#### 積み残しとして洗い出したもの

1. **entailment を立てていない大型制約が 17 本**。`set_constraint_entailed` を使うのは
   `logical`(7 箇所) / `value_precede`(3) / `lex_lesseq`(2) / `int_one_hot_channel`(2) だけ。
   all_different・cumulative・disjunctive・table・int_lin_eq などは充足済みでも
   フラグを立てないので、ソルバが毎イベント仮想呼び出しを続ける
2. `VariableSelector::select_linear` が table-layout で **43.14%**、opd で 10.96%
3. `NoGoodManager::propagate_eq_watches` の `unordered_map`（プロファイルの
   `std::_Hashtable` の正体）が code-generator 3.03% / opd 4.37%
4. `IntLinLe/Eq::save_trail_if_needed` が triangular で 29.72%・1.88 億回。
   本体は 10ns で、呼ばれる量そのものが本体

### 設計判断・理由

- **プロファイルと静的読みを両方使った**。サイズ順だけ見ても当たらない（comparison.cpp が
  最大だがホットではない）し、プロファイルだけでは「なぜ重いか」が出ない。
  diffn は「41.9% という異常値」をプロファイルが示し、コードを読んで
  「引数がコメントアウトされている」ことで原因が確定した
- **batch 方式と per-event 方式を区別して判定した**。`internal_var_idx` 無視は
  それ自体では無駄の証拠にならない。batch なら正しい設計で、per-event かつ
  O(n) 以上の走査を伴うときだけ無駄になる
- **diffn は軌道不変で済んだ**。ペア (j,k) が新しい伝播を出さないことの帰結で、
  golden 270/270 と rectangle-packing の fails 完全一致で裏取りした

## 2026-09-20 18:20 〜 19:30 積み残し④ — 前提が gprof のアーティファクトだった

**作業ブランチ**: `perf/constraint-trail-cache`（実装は撤回、コミットなし）

### 実施内容

ユーザ提案「`save_trail_if_needed` が必要かどうかを制約オブジェクトのフィールド
（フラグ）で判定すれば節約できるのでは」を実装した。

現状の判定は `trail_.empty() || trail_.back().first != save_point` で、**ヒープ上の
ベクタ末尾を読む**ためキャッシュミスしうる。これを `ConstraintTrail` に
`last_save_point_` スカラーを持たせて 1 回の比較にする（`rewind_to` / `clear` で
`trail_.back().first` と同期）。`ConstraintTrail` に入れたので int_lin_* 系・
table・nvalue・alldifferent など全利用者が対象。

**計測（交互実行、軌道不変なので固定時間の fails で比較）:**

| 対象 | 結果 |
|---|---|
| triangular（save_trail が 29.72% と出ていたモデル） | 比 **1.007**（base のばらつき自体が 5.9%） |

**差なし。** 前提だった 29.72% は gprof のアーティファクトだった。

### 設計判断・理由

- **gprof は「小さい関数 × 巨大な呼び出し回数」を過大評価する**。`-pg` では
  (1) 計装対象のインライン化が抑止され、(2) 呼び出しごとに `mcount` が走る。
  `save_trail_if_needed` は **1.88 億回 × 数命令**なので、計上された 1.92 秒
  （29.72%）の大半が計装オーバーヘッドだった。実際の `-O2` ビルドではこの判定は
  ほぼ無料で、削る対象がそもそも無かった
- **同じ物差しで今回の他の結果を検算した**。当たった 2 件は「呼び出し回数が中程度 ×
  本体が大きい」形で、いずれも wall-clock で裏取り済み:
  - `diffn_pairwise` 41.9%（220 万回 × O(n^2) 本体）→ 実測 2.08 倍
  - `select_linear` 43.1%（10.8 万回 × 全変数走査）→ 実測 −12.7%
  一方 `save_trail_if_needed`(1.88 億回) / `sync_selected_element`(8190 万回) /
  `energy_up_to`(9600 万回) は「巨大回数 × 数命令」側で、gprof の数字をそのまま
  読んではいけない帯域だった（energy_up_to のカーソル化は別途 wall-clock で
  裏取り済みなので有効）
- **アイデア自体は正しいが、対象が無かったので撤回した**。維持すべき不変条件
  （`last_save_point_` と `trail_.back()` の同期）が増えるだけになる
