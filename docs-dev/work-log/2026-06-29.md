  - `Model::clone()`（`model.hpp`/`model.cpp`）: 変数ディープコピー＋`Variable::model_` 戻りポインタ再設定、制約 clone、`constraint_ptrs_` 再構築、SoA/名前マップ/watch list/presolve スナップショットをコピー、trail/pending/scheduled はリセット。

- Phase 2（並列・bound 共有）
  - `static std::uniform_real_distribution jitter`（`constraint.hpp:329`）を `thread_local` 化。hot-path の他可変 static は無し（`next_id_` は clone がコピーctor経由で fork 安全、`const_counter` は parse 時のみ）。
  - `ParallelSolver`（新規 `include/sabori_csp/parallel_solver.hpp` / `src/core/parallel_solver.cpp`）: presolve 1 回 → N clone + fresh Solver + `apply_worker_config` → `std::thread` 起動/join。SAT は first-wins（`have_incumbent_` の exchange CAS + 各 solver `->stop()` 伝播）、UNSAT は全 worker 自然終了で判定。最適化は `best_obj_`(atomic) を共有、`external_bound_hook_` で各 worker の目的変数を restart 境界（root 状態）で締める。
  - `Solver::set_external_bound_hook` + `apply_external_bound`（`solver.hpp`/`solver_search.cpp`）。enqueue_set_max/min は単調（緩めない）で「incumbent より厳密に良い値」のみ許すため健全。
  - `main.cpp`: `-j N` フラグ（`N<=1` は既存経路で回帰ゼロ、`N>1` で `ParallelSolver`）。出力は `result_mtx` 下で直列化、タイムアウトは `g_parallel_solver->stop()`。多様化テーブル `build_worker_configs`（worker0=既定、以降 seed ずらし + ablation ローテーション）。
  - CMake: `find_package(Threads)` + `parallel_solver.cpp` をコアに追加（`src/core/CMakeLists.txt`）。

**設計判断・理由**

- **worker は master Solver の deep-copy ではなく fresh 生成**: 重い状態（activity/var_selector/nogood）は `init_search_no_presolve` が clone に対し再生成するため、warm-start するとむしろ多様性を損なう。atomic `stopped_` のコピー不可問題も回避。
- **bound 注入は restart 境界（root 状態）**: 既存の `enqueue_set_max/min` + `process_queue` 締め機構をそのまま再利用。他スレッドの Model は触らず共有は atomic のみ。健全性: 各 worker の探索は個別に完全なので、bound 共有は実在解より厳密に良い値だけに締める＝加速のみで最適性を壊さない。
- **stop 伝播は各 worker Solver の `->stop()` 転送**: 既存 `stopped_` atomic と `while(!stopped_)` ループをそのまま使い、探索ループへの変更ゼロ。`workers_ready_` フラグ + `reserve` で signal-handler からの走査を安全化。
- **clone 等価性の根拠**: presolve は rng を消費しない（one-hot も同様、community はデフォルト無効）ため、presolve をスキップした worker と原本 `solve()` は RNG 消費列が一致し、探索軌道・統計まで完全一致する。
- **多様化は探索時軸に限定**: one-hot 等 presolve 専用 ablation は master 1 回きりなので多様化軸に含めない。
- **find_all + portfolio（SAT）は重複列挙になるため単一スレッドにフォールバック**。

## 2026-06-29 ポートフォリオ多様化チューニング（VBS 決定論ベンチ）

**実施内容**

- ワーカー構成の多様化テーブル（`build_worker_configs`）を、決定論ベンチによる VBS 分析でチューニング。
- 方針: 並列の wall-clock はスレッド競合でノイズが大きいため、各候補構成を**単一スレッド・fzn直接・固定シード**で決定論評価し、VBS(virtual best = ワーカーの min)でポートフォリオ性能を予測 → 貪欲に構成を選ぶ。
- `SABORI_RESTART` env を追加（restart on/off を env で駆動。決定論評価の前提。`src/core/solver.cpp`）。
- `SABORI_PRINT_OBJ` env 設定時のみ目的値を stderr に出す小改修（`src/fzn/main.cpp`。golden は env なしなので不変）。
- ベンチ harness 新規: `benchmarks/minizinc_challenge/bench_portfolio_diversity.py`。MZC 16問（最適化13・SAT3）を flatten、10候補構成 × 16問を 4並列・12s で評価、VBS 貪欲ポートフォリオを構成。
- 分析結果で `build_worker_configs` を更新（`src/fzn/main.cpp`）。

**設計判断・理由**

- **activity優先固定(act_first)を不採用**: 単体スコア最弱(0.702)、solbat/elitserien など他構成が解ける問題を解けず(NOSOL)、VBS にも一切寄与しない。既存メモ [[mode_reward_rl]]（adaptive mix_p の EMA 強化学習が固定より強い）と一致。
- **MRV優先固定(fixed_mixp=0)と nogood無効を前方配置**: 単体は平凡だが多様性が高い（mrv は tppv14 で単独最良80、no_nogood は celar16 で単独最良63.1M vs base 69.1M）。貪欲 VBS で base の次に選ばれる。
- 新テーブル順: `base, mrv_first, no_nogood, no_restart, no_gradient, no_probe, no_temporal`（以降シードずらしで循環）。新 top-4 `{base, mrv, no_nogood, no_restart}` が**全構成 VBS 上限 0.930 に到達**（旧 top-4 {base, no_restart, act_first, no_nogood} は 0.900 止まり）。-j3 でも 0.904 vs 旧 0.883。
- **golden master を `-j 1` 固定に変更**（`tests/golden/run_golden.sh` の3箇所）: golden は決定論的な単一スレッド検証ツール。並列(-j>1)は本質的に非決定的なので、デフォルトスレッド数に関わらず単一スレッドに固定する。
- **`g_num_threads = 4;`（手動追加, arg parse 後）を削除**: -j フラグを上書きして常に4スレッドにし、default を非決定的にして golden を壊していた。削除し -j を機能回復、default=1 に戻した（ユーザ確認済み）。

**検証結果**

- ctest **261/261 green**（golden 復活）。
- 交絡注意: 各構成は別シードなので最適化では restart 無視 → `no_restart` ≈ シード変種。識別力があるのは16問中5問（celar13/tppv14/solbat14/celar16/elitser14）で、勝者は問題ごとに異なる＝多様性が VBS を押し上げる構図を確認。
- 実 -j4（チューニング済み）の end-to-end: **celar16 が base 69.1M → 63.2M**（no_nogood 効果、VBS最良近傍）、celar13 2859→2748、tppv14 84→82。ベース単独を大きく上回り VBS オラクル近傍。
- `-j` フラグ動作確認: default/-j1=単一スレッド(FULL stats)、-j4=並列(brief stats)。

## 2026-06-29 追補: restart スロットの問題タイプ別チューニング

**実施内容**

- ユーザ指摘（「リスタート完全オフより inner 初期予算を大きめに取る方が安全では」）を受け、restart 緩和機構を実装し SAT/最適化の両方で評価。
- `RestartController::set_initial_scale(double)` 追加（inner/outer の初期 conflict 予算を同係数でスケール、`inner<=outer` を保持）。`WorkerConfig::restart_scale`、`SABORI_RESTART_SCALE` env、`apply_worker_config` 配線。
- 新ベンチ `benchmarks/minizinc_challenge/bench_restart_sat.py`（SAT 11問: costas/word-equations/fillomino/solbat/monomatch を base/off/scale{2,4,8,16} で比較）。

**設計判断・理由（両ベンチ統合で restart スロットを問題タイプ別に分岐）**

- **SAT**: 完全オフ(restart_enabled=false)が**最悪**（solved 3/11, avg 0.215）、**moderate scale(=8)が最良**（solved 5/11, avg 0.364）。例: costas16 base 11.2s→sc4 1.3s（off は失敗）、we02_8 base 5.9s→sc8 0.2s。→ ユーザの直感が SAT では正しい（リスタート緩和が速く解く）。
- **最適化**: scale>1 は目的値を**悪化**（celar16 73M→86M, elitser は scale16 で解なし。アグレッシブな既定 restart が有益）、restart_enabled=false は **no-op**（最適化は restart 常時オン）で無害なシード変種。
- → `build_worker_configs(n, is_optimize)` に分岐: restart スロットは **SAT で `restart_scale=8.0`、最適化で `restart_enabled=false`**。呼び出し側 solve_satisfy=false / solve_optimize=true。

**検証結果**

- ctest 261/261 green。
- 機構動作: `SABORI_RESTART_SCALE` で restarts が 1→3441, 16→8, 64→0。
- end-to-end: costas16 単一スレッド base 7.3s → -j4（scale8 worker 含む）5.5s。
