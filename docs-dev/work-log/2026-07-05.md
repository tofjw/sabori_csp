### 実施内容
- **調査の発端**: `efm_cstr`（network_50_cstr, minimize）で `SABORI_THREADS=1` は
  `max_depth` が 2000 超、`SABORI_THREADS=2` は 280 で頭打ちになる理由を調査。
- **bound 共有説を棄却**: 両ワーカーとも `best=none`・結果 `UNKNOWN`（解ゼロ・incumbent
  ゼロ）を実測。external bound hook は incumbent 不在で `nullopt` を返すため未発動。
  当初の「worker1 の bound が worker0 を締める」説はこの問題では誤りと判明。
- **真因の特定**: `build_order`（初期変数順の構築）を presolve の前で走らせるか後で
  走らせるかの差。
  - single-thread（`init_search`）: `init_search_state` 内で **presolve 前**に build_order。
  - 並列 worker（`init_search_no_presolve`）: presolve 済み master を clone した後に
    build_order → **presolve 後**の状態で構築。
  - `build_order` は変数を decision/defined(instantiated)/unconstrained の 3 バケツに
    分けて各々 rng shuffle する。presolve が確定させた変数はバケツ所属が変わるため、
    同一 seed でも decision バケツの母集合サイズが変わり、Fisher–Yates の結果（=生き残り
    自由変数の順序）が変わる。→ 探索トラジェクトリが変わり dive 深さが変わる。
- **メカニズム実証**: env `SABORI_BUILDORDER_POSTPRESOLVE=1` で single-thread を
  post-presolve 化すると `max_depth=280` となり並列 worker0 と**完全一致**。1334↔280 の
  差はこのタイミング差が 100% の原因と確定。
- **A/B ベンチ**（`bench_buildorder_ab.py`, single-thread, 68問, 3 seed）:
  - seed 12345678: base 9 / var 16
  - seed 777:       base 10 / var 19
  - seed 42:        base 17 / var 11（逆転）
  - 合計: base 36 / var 46（post-presolve net +10、ただし問題・シード依存の諸刃）
- **option 1 実施**: post-presolve を**既定**に変更。旧挙動は
  `SABORI_BUILDORDER_PREPRESOLVE=1`（ablation）で復元可能。
- **テスト**: 261/261 pass。golden は `cumulative_ttef_push_est` 1件のみ差分だが、

### 設計判断・理由
- **性能単独では出荷根拠に不足**（seed 42 で反転する範囲のノイズ）。採用の主根拠は
  **アーキテクチャ整合**: 従来 single-thread ≠ 並列 worker0 という無自覚な非対称があり、
  これが「`-j1` と `-j2` で挙動が食い違う」交絡そのものだった。並列経路は構造上
  presolve 後にしか order を作れない（presolve 済み master を clone するため）ので、
  single-thread を post-presolve へ揃えるのが低リスクな統一点。
- 揃えたことで main.cpp の設計意図「worker0 = 単一スレッドより悪くならない軸」が
  実際に成立（両者ビット一致・同一 seed で同一変数順）。
- presolve は rng を消費しないため、build_order は両経路で「fresh seed の最初の rng 消費」
  となり、同一 seed で完全一致することを利用（コードコメントに明記）。
- 旧挙動を env で残したのは、問題依存で pre-presolve が勝つケース（yumi-static23,
  ihtc-2024 系）の再現・ablation 用。
