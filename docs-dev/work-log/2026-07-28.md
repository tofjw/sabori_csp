**設計判断・理由**

- **build ツリー用と install 用の .msc を 2 本立てにした**。CMake の build-tree export /
  install-tree export と同じ形。install を開発ループに挟むとブランチ切替のたびに prefix 側が
  古くなり、ベンチの信頼性が落ちる。build ツリー用 .msc の生成内容は 1 バイトも変えていない
- **install 先の .msc は絶対パスを焼かず相対パスで書く**。configure 時の `CMAKE_INSTALL_PREFIX` を
  埋めると、後から `cmake --install --prefix ...` で上書きされたときに嘘になる。
  相対関係は prefix に依存しないので configure 時に `file(RELATIVE_PATH)` で計算すれば足りる
  （絶対 BINDIR/DATADIR を指定された場合だけ絶対パスにフォールバック）
- **JSON の定義元を `sabori_csp.msc.in` に一本化**。`$<TARGET_FILE:>` が要る build 側は
  「configure_file でジェネレータ式を文字列のまま埋める → `file(GENERATE INPUT)` で展開」の
  2 段構えにした。これで定義の二重化がなくなり、孤児テンプレートも復活
- **mznlib は build のコピーではなくソースの正本から install する**
- **ブランチは main + `9c45cea` cherry-pick**。install ブロックが `SABORI_CSP_MZNLIB_SRC_DIR` に
  依存しており、この変数は `feature/subcircuit-scc` 側の mznlib clean copy コミットが導入したもの。
  cherry-pick して subcircuit の作業とは独立に main へ出せる形にした

## 2026-07-28 08:00〜13:00 phase hint の自己調整（EMA バンディット）と失敗率信号の検証

**作業ブランチ**: `feature/subcircuit-scc`

**実施内容**

- **`prob:0.2` の +11 を8シードで決着 → ノイズと確定**
  - 決着した141データ点（引き分け163を除く）で p02 の勝ちは76、期待値70.5、標準偏差5.94。**ズレは 0.93σ** で有意差なし
  - シード別 net は `+8, +5, −2, 0, 0, +4, −3, −1` で符号が正3・負3・ゼロ2。+11 の実体はほぼシード1と2（+13）だけ。4シードの時点で追加した後半4シードの寄与は合計ゼロ
  - 「狭サンプルは少数大勝に騙される」の典型例。最初に2シードで測ったのが不運だった
- **p_min の EMA バンディットを実装**（099f851、`PhaseRewardPolicy`）
  - `ModeRewardPolicy` と同じ構造。5段グリッド p_min ∈ {0, .25, .5, .75, 1.0}、信号=改善2.0/なければ1/(1+max_depth)、減衰0.5、floor 0.1、隣接0.1倍平滑化、報酬比例抽選
  - **上端 1.0 が従来の既定挙動**なので、バンディットがそれを最良と学習すれば既定へ戻れる（下振れしにくい設計）。初期バケットも 1.0
  - A/B（38問 × 8シード × 30秒）: `bandit vs full` **net +3（+0.25σ）**、`bandit vs p02` +1（+0.09σ）、`p02 vs full` +8（+0.67σ）。**固定値にすら勝てない**
  - 配線直後に golden master が落ちた。バンディットの `update_and_resample` が `rng_` を消費し、`SABORI_PHASE` 未設定でも軌道が変わっていたため。`phase_bandit_active()` ガードで修正
- **変数ごとの試行数/失敗数による失敗率信号を実装・検証**（a8a7426、`SABORI_PHASE=rate:<pmin>`）
  - 狙いは `activity_` の交絡（選ばれやすさ × 失敗させやすさ）の分離。率なら分離できるはずだった
  - 2026-07-22 の fail_rate 試作の敗因（20サンプル程度の率を信用）に対して、Laplace 平滑化 `(fail+1)/(try+2)` と最小試行数16のガードを入れた
  - **A/B を回す前に信号の分布を測ったところ、判別力が無いと判明**:

    | | 試行16回以上の変数 | 平均失敗率 | 標準偏差 | 率>0.5 | 率<0.1 | corr(activity, rate) |
    |---|---|---|---|---|---|---|
    | mario | 14 | 0.815 | **0.011** | 14/14 | 0 | +0.157 |
    | orthorio ch01 | 94 | 0.851 | **0.090** | 93/94 | 0 | **−0.398** |

  - ほぼ全変数が 80〜85% で失敗する。`rate/平均 ≈ 1` に張り付き既定挙動へ縮退する
  - 110分の A/B を回す前に分散を測ったので無駄撃ちを回避できた

**設計判断・理由**

- **「1で消えるなら記録して終わり」という前日の判断を撤回してバンディットに進んだ**。固定値が5点（0.0/0.1/0.2/0.5/1.0）すべて既定を安定して超えられないと8シードで確定した一方、`none vs full = −23` は軸そのものに大きな信号があることを示す。「固定値では駄目だがバンディットなら勝てる」は `mix_p` で実証済みのパターンなので、進む価値があると判断した（結果は不発）
- **バンディットの上端を従来既定に一致させた**。新機構が既存挙動を包含する形にしておけば、学習が失敗しても大崩れしない
- **既存の `ModeRewardPolicy` は触らず並置した**。実績のある部品を共通化するリファクタは巻き込み事故の危険がある。重複は将来まとめてよい旨をコメントに残した
- **実験フックはすべて既定挙動不変を厳守した**。RNG 消費（バンディット）、ホットパスのカウンタ更新（rate）、O(n) 走査（act）はいずれも既定経路から排除。既定の軌道が実装前と完全一致することを実測で確認（mario `fails=79218 restarts=1805`）
- **失敗率は A/B ではなく分布から否定した**。判別力の無い信号を110分かけて測る必要はない。「まず信号の分散を測る」は今後の型にする
