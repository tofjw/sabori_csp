## 2026-07-04 07:00〜13:00 LNS（大近傍探索）の実装と多角検証 → どの役割でも不採用

**実施内容**
- LNS を optimize ループに健全実装（既定OFF, `SABORI_LNS`）。`run_improvement_probe` を雛形に `run_lns_iteration`/`select_lns_fix_set`。incumbent 値へ可逆固定→予算付きサブ探索→`backtrack(root_point)` で巻き戻し。ノブ: `FRAC/BUDGET/FREQ/STALL/DESTROY(uniform/activity/community/related)/SCHED/ISOLATE/QUIET`。250 最適化 fzn で verdict+obj 一致、`SABORI_LNS` 未設定=`=0` byte 一致、260 C++テスト+golden 242 緑。
- チューニング（2023-2024 × 5seed, 30s, `bench_lns.py`）: 強制既定にすると **net -35〜-53（全シード一致で負）**。`iso≈noiso(-1)` で損失は機会費用（近傍探索が多様化リスタートより非生産的）と判明。`related < uniform(-22)`。
- 2025 対CP-SAT（`bench_compare.py`, Gecode検証）: base **9/6/4** → LNS-on は最良（高stall / quiet）でも **7/7/5**（stripboard / work-task-variation / mondoku が回帰）。既定OFFで base を byte 保存することを確認。
- quiet(side-channel)を2版試作しどちらも失敗:
  - v1（共有 best を締めるが redirect せず）: 締まった bound に stale hint で本探索が空回り→悪化。
  - v2（真の side-channel: `lns_best_` を本探索と分離 + `report_if_better` 単調出力 + rng/activity/temporal/best_assignment/**stats_** 隔離）: hijack 消滅・決定的化したが **time theft**（大近傍85%固定の伝播コスト）で広く回帰。**2025 対CP-SAT = 6/8/6 で最悪**。両版不採用、既定 `lns_quiet_=false`。
- ポートフォリオ VBS 実験（`vbs_2025.py`, 5アーム = base + seed2/seed3 + luby:100/constant:100）: base 9 → **VBS 11（+2, 回帰なし）**。seed3 単独=11, policy 各10。flip は ihtc-2024-marte(luby100) / proteindesign12(seed3)。
- restart/`outer` を記事 §5 と照合: 固定 Luby は不採用が正しい（**adaptive vs luby:100 = +14**, adaptive 勝ち）。`outer` の適応信号は情報ゼロ（scrambled と同点、+6/+7）。私の 2025 単年 luby 優位はノイズだった（記事の「loses on one seed」帯）。
- **LNS 固有カバレッジ確認**（`coverage_lns.py`, 2023-2025, 58 最適化問題, 強 seed ポートフォリオ base+seed2+seed3+no_nogood+mrv に積極LNSアーム stall1/freq1/frac0.3 を追加）: **LNS が全アーム中で厳密最良 = 0件（毎年0）, 対CP-SAT 勝ち上乗せ +0**。

**設計判断・理由**
- LNS の健全性は構造で担保: 近傍固定下の UNSAT は大域最適/UNSAT でない。`ReturnOptimal` は改善解受理後の root-only 伝播矛盾のみ（[[lcg-soundness-incident]] / [[allsol-incomplete-unsound-learning]] の轍を踏まない）。
- ポートフォリオでは best-of で LNS の負けは無害 → 唯一の論点は「他アームが到達しない解を LNS が固有に出すか」。答えは 0件。LNS の対base勝ちは**軌道多様化にすぎず新規到達能力ではない**。seed 変種が 30s で同じ盆地に time theft なしで安く到達し LNS を subsume。feature/mp の設計「seed-first・軸は弱い」と整合（LNS は特に高コストな弱軸）。
- 改善の本命は **seed 多様 portfolio**（VBS +2, 回帰なし）。残余は per-problem oracle gap(-37) = オンライン適応の問題で、固定 schedule でも `outer` 再設計でも埋まらない。

## 2026-07-04 20:00〜22:06 bin_packing_load ネイティブ化 → ihtc で CP-SAT 逆転

**実施内容**
- MZC2025 全20問題×全インスタンスの flatten 時間を計測し、30秒で終わらないものを特定
  - **gt-sort**: 全5件タイムアウト。`var set of int` 主体で `redefinitions.mzn` の `nosets.mzn` により set→bool 分解が爆発。chuffed/cp-sat も同様にタイムアウト＝set 展開が本質。単一 global 追加では解決不可（対象外と判断）
  - **ihtc-2024-marte**: i06/i11/i14 タイムアウト、i01/i03 も 126k/234k 行の巨大 fzn。原因は `bin_packing_load`（9箇所使用）の標準分解が O(bins×items) の reified 線形制約（`int_lin_eq_reif` 26k超）に展開されること
- `BinPackingLoadConstraint` をネイティブ実装
  - ステートレスな全再計算 batch propagator（`schedule_constraint_batch`+`propagate_batch`、cumulative と同方式）
  - bounds consistency: bin→load チャネリング（req/pos_add/neg_sum）＋ load→bin 逆伝播（include/exclude）。負重みも健全
  - `index_offset`（既定 0）で C++/Python は 0-based、FlatZinc は offset=1（InverseConstraint と同流儀）
- fzn registry（`sabori_bin_packing_load`, offset=1）・Python バインディング（既定 offset=0）・mznlib 再定義（`fzn_bin_packing_load.mzn`）を追加
- ブルートフォース解集合同値テスト（0-based 既定＋offset=1、健全かつ完全を検証）、golden 3本追加
- **落とし穴**: mznlib は3系統（canonical `share/` / build コピー / squashfs バンドル）。当初 squashfs だけに再定義を置き `bench_compare.py`（build コピーを使用）に反映されず「結果が違う」となった → canonical `share/minizinc/sabori_csp/` に追加＋`cmake -B build` reconfigure で解消

**設計判断・理由**
- 全再計算 batch propagator を採用: 状態を持たず trail 不要でバグ余地が小さい。ホットパスでないため定数倍より健全性・単純さを優先
- offset 方式（既定 0）: ユーザ要望「C++/Python は 0 始まり」に対し、element の `zero_based`（既定 1-based）より Inverse の offset（既定 0）が合致
- mznlib は canonical `share/` を唯一の編集先とする（build は生成物、squashfs は README 用の任意同期）
