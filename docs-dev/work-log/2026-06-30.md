## 2026-06-30 feature/ng2 から conflict learning を移植 + ポートフォリオ統合

**実施内容**

- feature/ng2 のコミット 3aff86e "Add conflict learning" を feature/mp に手動移植（cherry-pick は main.cpp/init_search 分割の分岐で不可）。
- コア（solver.hpp/solver.cpp/solver_frame.cpp）: 矛盾検出時に違反制約スコープが全確定なら、その割当を NoGood 化する conflict 学習。`set_conflict_learning`、`capture_conflict_explanation`、`conflict_learning_`/`conflict_expl_`/`conflict_expl_ok_`、record_constraint_call での capture 呼び出し、try_enumerate_values/try_bisect_branches での learn_from_conflict。init_search_state でクリア。

**設計判断・理由**

- 健全性: 個々の NoGood は「全確定スコープで違反した割当」＝定義上 unsat なので偽 UNSAT を生まない。部分割当（未確定変数あり）の bounds 矛盾は健全な Eq 説明を安価に作れないため bail（decision-path 学習にフォールバック）。スコープ<2 の制約も除外。
- 既定 off: メモ [[conflict-learning-C-retain]] のとおり性能 net±0（problem 依存の諸刃）。並列ではこれが好相性 — 多様化軸として 1 ワーカーに載せ、効く問題で VBS を押し上げる。
- 多様化軸は case 6（%7）なので -j<=7 では既定 off、-j8 で 1 ワーカーが conflict 学習 ON（-C 指定時は逆に 1 ワーカーが OFF）。-j4 など常用域の挙動は不変。

**検証結果**

- **健全性: 全242コーパスで base と `-C` の解集合・ステータスが完全一致**（-a, 解ブロックをソート比較, mismatch=0）。偽 UNSAT/解漏れなし。
- ctest 261/261 green。
- conflict 学習が稼働: SABORI_CONFLICT=1 で conflict nogood 学習（celar13 nogoods 377→204・ng_prune 265→356 等、探索が変化）。net±0 の挙動。

## 2026-06-30 追補: conflict 学習を多様化メンバーとして VBS ベンチ → 前方昇格

**実施内容**

- conflict 学習（SABORI_CONFLICT=1）を bench_portfolio_diversity.py の構成プールに追加（"conflict"）し、MZC 16問で VBS 貪欲分析。
- 既存 results.json（10構成）に conflict 構成を増分実行してマージ → 再分析。

**結果・設計判断**

- **conflict 学習は理想的な多様化メンバー**: 単体スコアは**最下位（0.684）**だが、貪欲 VBS で **2番目に選ばれ Δ=+0.062 と最大の限界寄与**（mrv_first +0.041 を上回る）。
- 寄与源は **elitser14 で単独最良（obj=6, 他構成は 7 or 解なし）**。「単体最弱だが他が解けない問題を解く」典型的な好メンバー（メモ [[conflict-learning-C-retain]] の「問題によっては効く」を VBS で裏付け）。
- conflict の勝ちは**最適化**(elitser)、restart-scale8 の勝ちは**SAT**(costas/we)だった → 3番目の多様化スロット(case 2)を**問題タイプ別**に変更:
  - 最適化 → conflict 学習（worker3, -j4 で出現）
  - SAT → restart 緩和(scale8)（worker3）
  - 相手側の軸は case 6（-j8）に回す（最適化の case6=restart no-op シード変種, SATの case6=conflict）。
- conflict を -j8(case6) から **-j4(case2, 最適化のみ) に前方昇格**。常用域 -j4 で conflict worker が効く。

**検証結果**

- ctest 261/261 green。健全性は前回の全242コーパス base==-C 一致で担保。
- end-to-end: **elitser14 を -j4 で obj=6**（単一 base=8）。conflict worker が単独勝ちを届けることを確認。

## 2026-06-30 追補3: 多様化軸を VBS インパクト順に採用

**実施内容**

- `build_worker_configs` の rotation を「VBS 限界インパクトの大きい順」に並べ替え。worker0=base 据え置き、worker1=最大インパクト軸、worker2=次…と、-j を増やすほど影響の小さい軸が後から足される構成に。
- 影響順は問題タイプで異なるため is_optimize で2系統に分岐:
  - **最適化**: conflict(Δ+0.062) → mrv(+0.041) → no_nogood(+0.011) → gradient/probe/temporal(~0) → restart(no-op)
  - **SAT**: restart緩和sc8(最良) → conf_sc8(併用,VBS2位) → mrv → no_nogood → gradient/probe/temporal

**設計判断・理由**

- 以前は固定順（mrv→nogood→restart/conflict→...）で、最大インパクトの conflict が case2(-j4) や case6(-j8) に埋もれていた。VBS の限界寄与順に並べ替え、小さい -j ほど効く軸を確保。
- conflict を最適化 worker1 に昇格 → **-j2 で既に効く**（以前は -j4 必要）。

**検証結果**

- ctest 261/261 green。
- end-to-end: **elitser14(最適化) が -j2 で obj=6**（単一 base=8）。conflict が worker1 として -j2 から効くことを確認。
