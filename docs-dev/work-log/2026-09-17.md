### 設計判断・理由

- **全部入りを先に作ってから絞った**。「衝突がどこに出るか」「テストが通るか」を
  机上でなく実物で確かめないと、除外判断の前提（どこが絡み合っているか）が立たない。
  結果として subcircuit の二重実装という、コミットログからは見えない問題が出た。
  捨てずに `integrate/more-constraint-full` として残してある
- **subcircuit は main 側を採用**。main 版は到達可能性フィルタ（`SABORI_SUBCIRCUIT_REACH`）と
  パス端点リンク方式を持ち、branch 版（全再計算 batch）の上位互換。branch 版のテスト 3 本は
  `sabori_subcircuit` エイリアス経由で main 実装に通し、expected は再録不要だった
- **cherry-pick であってマージではない**。既定変更と opt-in を落とすのが目的なので、
  ブランチ全体を持ってきて revert する形は取らなかった。
  代償として `feature/more_constraint` の ahead 数は 74 のまま減らない
- **work-log `2026-07-07.md` は今回 main に入った作業のセクションだけ収録した**
  （value_precede / lex / connect CHECK_FAIL）。
  未マージのコード（int_eq_imp / groupsplitter / entailment / subcircuit / perf マージ）の
  記録を main に置くと「やったことになっているのに main に無い」状態を作り、
  昨日直したばかりの取り違えを再生産する。ファイル冒頭に残置先を注記した
- **perf 群と opt-in アームを見送った理由**（ユーザ判断）: ブランチ側のベンチ検証
  （14 年通算 net +14 / CHECK FAIL 0）は **main の element support tracking と
  div/mod チャネルが入る前**のもので、相互作用が未計測
