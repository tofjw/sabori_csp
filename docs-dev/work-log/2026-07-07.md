    strict 要求時 <）bounds 強制、x[i] < y[i] 保証で充足済み停止

## 2026-07-07 09:30 〜 10:30 connect CHECK_FAIL 調査 → 検証機構の偽 FAIL と特定・修正

**結論: sabori の健全性バグではない**
- sabori の解（obj=7784180）を「モデル本文 + pin 連結」方式で gecode 検証 → **SAT**
  = 解は正しい。bench の verify_solution が偽 FAIL を出していた

**根本原因（2段階）**
1. MZN レベル検証（`include + constraint var=value`）の構造的欠陥:
   connect モデルは `is_fixed()`（L2841）や `lb_array()` 境界という
   **flatten 順依存の構文**を含む。pin を同居させた checker では is_fixed の
   分岐が変わり「sabori が解いたモデルと別物」になる（include 方式=UNSAT、
   連結方式=SAT を同一 pin 集合で実証）
2. 救済用の FZN レベル検証（この誤検出のために設計済み）が **CHECK_SKIP に脱落**:
   gecode の flatten が出力変数 2525 個中 2243 個を定数化し .ozn に
   `int: name = 4;` の literal として置くため、FZN 名でのカバレッジが
   201/2525 (8%) となり閾値 (>50%) を割っていた

**修正 (bench_compare.py `_verify_fzn`)**
- .ozn の literal 固定 (`int: name = N;` / `bool: name = true|false;`) を解析し、
  該当する出力変数は制約を張らず **Python 側で直接値比較**（不一致=即 FAIL、
  一致=カバレッジに算入）→ connect のカバレッジ 8%→97%、救済が機能

**検証**
- connect: fresh solve → verify_solution = **CHECK_OK**（literal 2243 個の照合込み）
- 回帰スポット: mario13 / stripboard25 / neighbours24 = CHECK_OK 不変
- FZN 検証の健全性根拠: pin なしの standalone flatten は sabori と同じ
  is_fixed 分岐を辿るため意味論が一致する

**気づき**
- MZN レベル検証は order 依存構文を含むモデル一般で両方向に誤りうる
  （今回は偽 FAIL だが偽 OK も理論上可能）。FZN 側が今回の修正で
  実質的な最終判定者として機能するようになった
